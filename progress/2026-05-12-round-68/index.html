    2. Decisions and rationale¶

    D1 — Why commit R68 (planning-round archetype, 5th confirmation)¶

    R57 (Arc A commit after R56 skeleton), R61 (slice 4 scoping after v0.5.0), R66 (Arc A item 2 audit), and R68 all fit the "post-release planning round" archetype. CONTEXT.md has this invariant on the wall since R61. This round strengthens the pattern: Arc B slice 1 scope is committable in ≤90 min (research + design + ADR Draft + roadmap + progress + CONTEXT refresh) from pytest clean → push. Single-slot budget held.

    D2 — Why Anthropic Agents SDK over OpenAI Agents SDK¶

    Three-way tie-break (both pass ADR-016 mapping cleanliness, both have rising ecosystem):

    1. Strategic fit: MCP-native shops are underserved by existing observability tools (Langfuse/Phoenix lack MCP-aware semantics). OpenAI Agents SDK's competitive field (OpenAI's own tracing) is more crowded.
    2. First-user appeal: Chronos's "agent pdb + git" framing fits MCP's tool-call interception point more naturally than OpenAI's internal Responses API.
    3. Leverage tail: MCP standardisation (2024-Q4) is still compounding through 2026-H2. OpenAI Agents SDK peaks narrower.

    The pre-authorised fallback clause hedges the one real risk (MCP fork-lifecycle) without forcing a round-level re-plan.

    D3 — Why 5 rounds for Arc B slice 1 (not 3)¶

    CrewAI Arc B precedent was R49-R55 (7 rounds, stretched). N-run compare was R58-R60 (3 rounds, tight). Arc B slice 1 targets 5 rounds because live-smoke gating requires two dedicated rounds (record + fork) whereas pure-function Arc A slices didn't. Bundle shape:

    Round Role Analogue
    R69 Risks spike + ADR-026 Draft → Accepted R57 Arc A commit
    R70 Core adapter scaffold + duck-typed tests R51 CrewAI scaffold
    R71 Live-smoke (ANTHROPIC_AUTH_TOKEN) R53 CrewAI live-smoke
    R72 Dogfood + v0.7.0a1 alpha R54 CrewAI alpha
    R73 Fork primitive + fork live-smoke (novel — Arc A had no equivalent)
    R74 v0.7.0 release cut R55 / R60 / R64 / R67

    5. Findings (five new, for CONTEXT §5 wall)¶

    F1 — Post-release planning-round archetype 五连 (R56/R57/R61/R66/R68)¶

    Five confirmations of the "post-minor-release planning round fits single-slot md-only budget with 4 artifact ceiling" pattern:

    • R56 Phase 4 charter skeleton → 2 ADR artifacts
    • R57 Arc A commit → 2 ADR artifacts (in-place promotion + superseder)
    • R61 slice 4 scoping → 3 md artifacts (Draft ADR + research + roadmap)
    • R66 Arc A item 2 retro-audit → 4 md artifacts (audit + design + Draft ADR + roadmap)
    • R68 Arc B kickoff → 4 md artifacts (research + design + Draft ADR + roadmap)

    Structural constant: ~60-90 min single-slot, 3-4 md artifacts, no code, no tag cut. Promote to CONTEXT long-term invariant.

    F2 — Pre-authorised fallback clause as drift-prevention pattern (R68 新)¶

    R26-era lesson: an ADR that commits to only one path without backup forces a round-level re-plan when the path blocks. Cost: 10+ rounds of drift (R26 adapter interface stall).

    R68 innovation: ADR-026 §Fallback explicitly lists (framework, criteria, swap scope). If primary blocks at risks-spike stage, swap is pre-authorised — no re-ADR, no replanning detour. Criteria are hardened (3 must-all-hold) to prevent trivial fallbacks.

    Candidate invariant: "Every scope-commit ADR should name one fallback with gate criteria." Pending second confirmation in a future scope ADR (ADR-027?).

    F3 — Arc B has a 5-round slice shape vs Arc A's 3-round (R68 prediction)¶

    Arc A slice 4 was R62/R63/R64 (3 rounds: core/surface/proof+release). Arc B slice 1 pre-budgets R70/R71/R72/R73/R74 (5 rounds) because adapter shipping requires live-smoke gating (record + fork), not just proof. This is the same stretch CrewAI Arc B had (R49-R55, 7 rounds, further stretched by adapter-interface discovery).

    Refinement to R60 bundle-shape invariant: "Arc slice = core + surface + proof = 1 minor version" is Arc A specific. Arc B adapter slice = scaffold + live-smoke + alpha + fork + GA = 5 rounds = 1 minor version. Two bundle-shape families co-exist. Pending R74 ship to confirm.

    F4 — Stale remote-tracking ref trap 六连 (R48-B/R59/R60/R61/R63/R68)¶

    Sixth confirmation of the same trap. git status said "ahead by 1 commit"; git ls-remote origin main said HEAD==origin. git fetch origin main refreshes. Every cron slot inherits this staleness after prior-slot push because local tracking ref wasn't updated. Candidate skill addition: cron-slot-handoff-recovery skill already mentions the trap; R68 adds 6th-confirmation evidence — no skill update needed, pattern is codified.

    F5 — Arc B candidate table in ADR-023 stale at 3-week granularity (R68 新)¶

    ADR-023 §Arc B table (2026-04-22 snapshot, R56) listed "Swarm / Assistants v2 / Anthropic Agents SDK / Letta / LiveKit / Generic OTel". R68 survey (2026-05-13, 3 weeks later) found:

    • 2 of 6 still viable (Anthropic Agents SDK, Letta).
    • 2 rejected by ecosystem shift (Swarm lost favor; Assistants v2 API-only).
    • 2 niche-only (LiveKit, Generic OTel).
    • Plus 2 new candidates not in R56 table (OpenAI Agents SDK, Pydantic AI).

    Lesson: candidate tables in scoping ADRs decay fast during high-velocity framework periods (2026-H1 had MCP standardisation + Swarm-to-Agents-SDK transition + Pydantic AI release). Refresh cadence: 2-3 weeks max before commit. R68 refresh was well-timed — a further delay would have locked us into a stale evaluation.
