    R77 — slice 3a-P1: multi-block tool_use_ids extension (ADR-026 §5.1.1)¶

    Date: 2026-05-15 (Beijing) · Window: 07:47 CST autonomous cron Predecessor: R76 (ADR-026 §5.1 single-block state_after.tool_use_id) Successor: R78 (TBD — slice 3a-P2 or slice 3b) Phase: 4 Arc B slice 3a — recorder-side JOIN-anchor instrumentation Status: ✅ shipped — 616 → 619 tests, ruff clean, ADR amended in-place.

    §0 — Cover¶

    R77 extends the R76 single-block state_after['tool_use_id'] contract (§5.1) to the multi-block case (§5.1.1). When an AssistantMessage carries >1 ToolUseBlock (batched parallel tool dispatch) or a UserMessage carries >1 ToolResultBlock, the recorder now surfaces an ordered state_after['tool_use_ids'] (plural) list. Mutual exclusivity is binding: singular and plural fields MUST NEVER coexist on the same Node. Slice-3 SQL consumers JOIN 1:N via json_each(state_after->>'tool_use_ids'). No schema change — just a contract pin extending §5.1's JSON-bag stamping. Three new unit tests pin the contract; the adapter-1-3 zero-regression streak holds at R52→R77 = 25 rounds.

    • Test baseline: 616 passing / 7 skipped (live-gated). Confirmed via uv run pytest -q --no-cov before any edits.

    • _translate() in recorder.py already isolated the len(tool_blocks) == 1 and len(result_blocks) == 1 branches in symmetric arms — the natural extension point for a len(...) > 1: sibling arm on each side.
    • Working tree clean, git status reported nothing to commit.

    §2 — Work done¶

    §2.1 Recorder patch (src/chronos/adapters/anthropic_agents/recorder.py)¶

    Added two symmetric elif len(...) > 1: branches inside _translate():

    • Assistant side (AssistantMessage with >1 ToolUseBlock): comprehension over tool_blocks filtering by isinstance(getattr(b, "id", None), str) and b.id, attribute-access on the truthiness check (B009-clean). If non-empty list survives the guard, state["tool_use_ids"] = ids (no singular tool_use_id set).
    • User side (UserMessage with >1 ToolResultBlock): same shape, reading b.tool_use_id instead of b.id.

    Order is preserved (no sorted(), no set()) so consumers can pair use[i] ↔ result[i] by index. Mutual-exclusivity guarantee is structural: the len == 1 and len > 1 branches are mutually unreachable per Node.

    Net diff: ~16 lines added, recorder imports / module API untouched.

    §2.2 Unit tests (tests/unit/test_adapter_anthropic_agents.py)¶

    New §6.2.1 section pinning the contract (3 tests, all hermetic):

    1. test_record_multi_tool_use_block_persists_ids — AssistantMessage with 3 ToolUseBlocks. Asserts ordered list match (asst.state_after["tool_use_ids"] == ids) and singular field absent.
    2. test_record_multi_tool_result_block_persists_ids — full round-trip (Assistant 2-use + User 2-result). Asserts both Nodes carry byte-identical plural lists (the JOIN keyset) and neither carries singular.
    3. test_record_mixed_count_keeps_singular_and_plural_separate — regression guard. Stream interleaves a single-block tool round-trip with a 2-block batched-use. Asserts the singular Node has only tool_use_id, plural Node has only tool_use_ids, with no cross-talk. Future refactor that collapses the two fields fails loudly.

    Tests use the existing _blk / _msg / _aiter helpers and the @dataclass-based _StubBlockBase (R76's id slot already in place). Disambiguation in the mixed-count test goes by which key is present in state_after (not by node ordering) — robust against any future node-ordering change.

    §2.3 ADR-026 §5.1.1 amendment¶

    Added new §5.1.1 sub-section directly after §5.1's "Out of scope" list (per R57 doctrine — amendments land in-place). Updated §5.1's out-of-scope bullet that previously called multi-block "reserved for a future slice" — now reads "resolved by §5.1.1 below".

    §5.1.1 contains:

    • Contract (4 MUST clauses): use side plural list, result side plural list, byte-identical JOIN keyset, mutual-exclusivity binding (singular and plural fields cannot coexist on the same Node).
    • Test enforcement: cites the 3 §6.2.1 tests by name.
    • Consumer pattern: SQL recipes for both single-block (->>) and multi-block (json_each) JOIN, side-by-side, ready for slice-3.
    • Out of scope for §5.1.1: asymmetric block counts (handled as JOIN gap, no special recorder logic), cross-turn batching (not observed in current SDK traffic).
