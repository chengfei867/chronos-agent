    Round 57 — Phase 4 kickoff: Arc A committed + N-run compare design doc¶

    Slot: 2026-05-09 CST 01:17–01:40 (inside 0-11 cron window) Agent: Hermes Agent (autonomous, baidu-int Claude Opus 4.7) Archetype: Phase-kickoff strategy round (design-first, zero code) Outcome: ✅ on-plan — R56 §6 Option A + Option C bundled

    1. Going in¶

    R56 closed out post-release polish, marked Phase 3 ✅ COMPLETE in docs/roadmap.md, and wrote ADR-023 as a Draft skeleton listing three candidate Phase 4 arcs (A Depth / B Ecosystem / C Plumbing) with the decision deliberately deferred to R57. R56 §6 laid out three options for R57:

    • Option A (首选, 60-90 min): Arc A scoping — write docs/design/n-run-compare.md
    • Option B (备选, 60-75 min): Arc B research — adapter #4 survey
    • Option C (最快, 30-45 min): ADR-023 Draft → Accepted (just lock arc)

    R57 chose to bundle Option A + Option C — write the design doc and lock Arc A in the same round. R56 explicitly called this out as the "90-120 min in budget" combination. Budget hit: ~25 min wall, well under.

    2. Decision: why Arc A (recorded here for next-round readers)¶

    The argument for Arc A over B/C is in ADR-023 §"Decision (R57 — Arc A committed)" and won't be repeated in full here. Short version:

    1. Leverage — Arc A turns already-recorded data (every run, every node, every fork across LangGraph/AutoGen/CrewAI) into more insight without adding adapter surface. Three adapters is enough breadth for 2026.
    2. Low risk — ADR-006 two-run alignment is battle-tested since R39-A. N-run is a pure function over N−1 copies of that alignment. No new semantic model.
    3. Real internal demand — during spike12/spike13 dogfooding I literally had three terminal tabs open running chronos diff A B, diff A C, diff A D. That's the user story.
    4. Arc B premature — fourth adapter is breadth; we just bought breadth at v0.4.0. Diminishing returns unless a specific cohort asks.
    5. Arc C demand-driven — zero external users, zero signal, so Docker / LAN-sharing / plugin system stay deferred.

    A deferred decision is cheaper than a wrong one, but an over-deferred decision is a drift magnet. R57 is the right slot: headroom exists, signal is clearer than R56.

    5. Key learnings to carry forward¶

    5.1 In-place ADR promotion is a valid pattern (R57 new)¶

    When a Draft ADR's Context + candidate framing remains correct and only the decision changes, promote in place (Status + Decision + Follow-ups rewritten; Context + Options preserved). Do NOT open a new ADR-024 that duplicates the framing. The top-of-file Status line records the history ("Accepted (skeleton R56; Arc A commit R57)"), so provenance is preserved without double-maintenance. This applies to:

    • Any "skeleton + decision-deferred" ADR pattern (see ADR-023 shape).
    • Any ADR where the Options section is the reusable artifact.

    When this doesn't apply: if the new decision invalidates the original framing (e.g. rejects all listed options and invents a new one), open a new ADR and mark the old Superseded.

    5.2 Phase-kickoff round archetype (R57 new)¶

    The R56 → R57 sequence reveals a two-round pattern for phase transitions:

    1. Post-release polish round (R56): close out previous phase on roadmap + README/guide adapter matrix refresh + draft-skeleton ADR for next phase with explicit decision-deferred.
    2. Phase-kickoff round (R57): promote the skeleton ADR (or replace it), land the first slice's design doc, update roadmap priorities from "candidate" to "ACTIVE"/"DEFERRED". Zero code.

    Both rounds are docs-only. Both are single-slot. Both preserve the adapter zero-change streak.

    Candidate skill: chronos-phase-transition-pattern — defer authoring until the next phase transition gives a second data point (currently only R56→R57 validates it; need R61→R62 or similar to confirm the archetype).

    5.4 CLI-first → API-first → Web-optional ordering for new features (R57 new)¶

    The design doc explicitly orders delivery: CLI (R59) before API-via-CLI- shape-lock (R59 same round) before Web (R60, optional). Rationale: CLI is the JSON contract test. Writing the CLI first forces the JSON shape to be decided before React props harden assumptions. This inverts the instinct to ship Web first for demo-ability.

    Applicable to: any new verb/endpoint pair. Applicable to: the next Arc A second slice (fork-tree DAG viz) — same ordering planned.
