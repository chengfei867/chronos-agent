    Round 45-A — PH3-03 Fork-plan downstream side-effects preview (v0.3.1)¶

    Date: 2026-04-25 CST ~16:00 Branch: main Release: v0.3.1 Tests: 435 pass / 2 skip / 94% coverage (+8 from v0.3.0), cli/fork.py 97%

    Goal¶

    Land PH3-03 — close the effect-aware UX loop on the CLI side. v0.3.0 (R44-A) gave the Web UI a per-node Fork warning banner; PH3-03 brings the same honesty to chronos fork plan so terminal users see "if you fork here, N dangerous downstream nodes will re-execute" before they save the plan.

    Zero schema change, pure CLI-layer enhancement. Continues the R43 / R44-A line: ADR-019 — Chronos does not sandbox, it warns.

    Deliverables¶

    1. Pure helper — src/chronos/cli/fork.py::build_effects_summary¶

    def build_effects_summary(
    downstream_nodes: Sequence[Node],
    *,
    dangerous: frozenset[str] = DANGEROUS_EFFECTS_DEFAULT,
) -> dict[str, Any]:

    Returns {total, dangerous_count, tag_counts, samples}: - total — count of downstream nodes (step_index > parent.step_index) - dangerous_count — subset that carry any tag in dangerous - tag_counts — {tag: int} across all downstream nodes (sorted alphabetically on render) - samples — up to 3 dangerous nodes, each {step, name, tags} (prevents 50-node dangerous runs from flooding the terminal)

    Defensive: if metadata["effects"] is missing or not a list (malformed runs), the node is treated as tag-less rather than crashing. No I/O, no console — trivial to unit-test.

    2. Renderer — render_effects_preview(summary, console)¶

    Rich Panel(border_style="yellow") titled "Downstream side-effects preview":

    ⚠ 4 dangerous / 5 total
breakdown: db=1, external=1, fs=1, network=2
• step 1: fetch_api (network, llm)
• step 2: write_file (fs)
• step 3: db_insert (db)
… and 1 more
Chronos does not sandbox forks — review before running (ADR-019).

    Silence principle: renders nothing when total == 0 (forking at the last node) OR dangerous_count == 0 (pure-LLM downstream). Prevents false-alarm fatigue.

    3. CLI wiring — render_plan_preview + fork_plan_command¶

    • render_plan_preview() gains effects_summary: dict | None = None kwarg (backward-compatible — existing callers pass nothing and get the old behavior).
    • fork_plan_command() after parent resolution: 
      downstream = [n for n in nodes if n.step_index > parent_node.step_index]
effects_summary = build_effects_summary(downstream)
      Both emit paths (JSON stdout + Python-literal stdout) pass it to render_plan_preview.

    4. Tests — 8 new in tests/unit/test_fork_cli.py¶

    Helper block (pure-function tests, no Click runner): - empty downstream → {total:0, dangerous_count:0, tag_counts:{}, samples:[]} - pure-LLM downstream → dangerous_count == 0, tag_counts == {"llm": N} - mixed tags → correct dangerous count + alphabetical tag breakdown - >3 dangerous → samples capped at 3, still reports correct dangerous_count - malformed metadata["effects"] = "not a list" → treated as no tags, no crash

    CLI block (CliRunner against synthesized run + SqliteStore): - mixed run, fork mid-run → stdout contains Downstream side-effects, dangerous count, tag breakdown - fork at last node → stdout does not contain the panel - pure-LLM downstream → stdout does not contain the panel

    5. Bonus fix — test_cli_info phase-marker stale assertion¶

    R44-A bumped the chronos info CLI output to "Phase 3 on-ramp" but didn't update tests/unit/test_cli.py::test_cli_info which still asserted "phase 2". Full-suite run in R45-A caught it. Fixed + listed in v0.3.1 CHANGELOG. Lesson added to CONTEXT §5: release cut must run full pytest -q, not just the test file of the feature branch.

    Key facts (pinned to CONTEXT.md §5)¶

    1. Per-run linear downstream, not DAG-topological: step_index > parent.step_index matches the replay/fork consumer mental model (forking replays the timeline from that point forward). Walking the DAG via parent_node_id edges is a Phase 4 concern and would change semantics.
    2. Silent-by-default: no panel at total == 0 or dangerous_count == 0. ADR-019's honesty is "warn when it matters", not "spam on every fork".
    3. Sample cap 3 + … and N more: realistic ergonomic cap; enough to give users a feel for what's downstream without flooding a terminal.
    4. Defensive metadata parsing: metadata["effects"] treated as optional-and-possibly-garbage input. One-line isinstance(x, list) guard, no recovery magic.
    5. Pure helper / renderer split: build_effects_summary() is easily unit-tested (no I/O, no console); render_effects_preview() is a thin renderer smoke-tested via CLI key-string assertions. Good pattern for future CLI additions.

    What this closes¶

    Phase 3 "make users feel side effects" now has three entry points all lit up: - Adapters auto-tag nodes (R44-A, v0.3.0) - Web drawer: per-node effect Tags + amber warning Alert + danger Fork button hook (R44-A, v0.3.0) - CLI fork plan: downstream side-effects preview Panel (R45-A, v0.3.1) ← this round

    What this does NOT close¶

    • TreeView.tsx still doesn't pass onFork prop to NodeDetails, so the danger Fork button predrawn in R44-A is still unlit. Candidate R46-A.
    • roadmap §Phase 3 first bullet still says "side-effectful tool sandboxing" — charter-level change, needs user sign-off. Candidate R46-B.
    • No forking-safely.md guide yet synthesizing v0.3.0 + v0.3.1 behavior for external users. Candidate R46-C.
